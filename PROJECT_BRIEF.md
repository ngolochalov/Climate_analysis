# Исходный промт для агента: анализ влияния погоды на токосъём (СЛД Кандалакша)

> Этот файл — стартовый контекст для работы с Claude в VS Code. Он фиксирует задачу,
> уже принятые архитектурные решения и план. Решения в разделе «Архитектура» приняты
> осознанно — не пересматривай их без явного запроса, опирайся на них.

## 1. Контекст и цель

Исследовательская работа УрГУПС: анализ влияния климатических и погодных факторов
района эксплуатации сервисного локомотивного депо (СЛД) **Кандалакша** (Мурманская
область, полярный климат) на условия токосъёма и потенциальный износ вставок
токоприёмников. Результат — **база данных климатических факторов риска** + аналитика.

**Важная граница работы.** Эксплуатационные данные депо (пробеги, замеры износа
вставок, ремонты) НЕ предоставляются. Прямое установление причинно-следственной связи
«погода → фактический износ» **не является целью**. Работа — это климатологический
анализ открытых данных плюс экспертная классификация рисков на основе литературы.
IT-часть строит инструмент и аналитику, а не модель износа.

Литературный обзор и обоснование пороговых значений рисков ведутся параллельно другими
участниками команды (3 человека всего). Эта IT-часть отвечает за: выгрузку данных,
БД, обработку, движок критериев и критических периодов, визуализацию.

## 2. Анализируемые параметры (из ТЗ, п. 8)

Температура воздуха (°C), относительная влажность (%), осадки (мм), снег/мокрый снег
(факт), гололёдные явления (факт), скорость и порывы ветра (м/с), атмосферное давление
(гПа), число переходов температуры через 0 °C, длительность отрицательных температур
(часы/сутки), температурные перепады (°C).

Параметры явлений (мокрый снег, гололёд) — это **наблюдаемые факты**, а не расчётные
величины. Это определяет выбор источников (см. ниже).

## 3. Архитектура (решения приняты — следуй им)

### 3.1 Источники данных — ОБЯЗАТЕЛЬНО ОБА (гибрид)

Использовать **два источника одновременно**, это требование:

1. **Наблюдения станции Кандалакша (ВМО 22217)** — через rp5.ru / meteo.ru
   (ВНИИГМИ-МЦД). Срочные наблюдения (~каждые 3 часа). Это **основной** источник,
   особенно ради кодов текущей погоды WW — фактически наблюдённых явлений (гололёд,
   изморозь, мокрый снег, ледяной дождь), которых нет в реанализе. Минус: возможны
   пропуски в ряду.

2. **Реанализ ERA5 через Open-Meteo Historical Weather API** (`/v1/archive`) —
   почасовые данные, без пропусков, без авторизации, бесплатно, лицензия CC BY 4.0.
   Используется для **восполнения пропусков** в непрерывных числовых рядах станции
   и как **кросс-проверка**. Минус: это модельное поле ~25 км, не локальные замеры,
   и оно не содержит наблюдённых кодов явлений.

**Принцип объединения:** станция — приоритетный источник; ERA5 заполняет пропуски и
служит сверкой. Каждая запись помечается полем `source` (`station` / `era5` / `filled`).
Прокси-определения явлений (например «влажность > 90 % при T около 0 °C» вместо
наблюдённого кода) помечаются отдельно — методическая честность обязательна, на защите
про источник и про восполнение спросят.

Период данных: 10–15 лет (зафиксировать одну дату выгрузки и период в конфиге — повторная
выгрузка в середине проекта ломает воспроизводимость).

### 3.2 СУБД и стек

- **SQLite** как основная СУБД (один файл, легко приложить к отчёту и передать на
  проверку, без развёртывания сервера). PostgreSQL — не требуется.
- **Python 3** + pandas, numpy, scipy, requests, **SQLAlchemy** (ORM-модели дают
  автогенерацию `CREATE TABLE` = SQL-скрипты для отчёта, и удобную загрузку через
  pandas `to_sql`).
- Визуализация: matplotlib / seaborn; Power BI — опционально, только для итоговой
  интерактивной панели поверх готовой SQLite.
- Пороги риска держать в `config.yaml`, НЕ в коде — они меняются по мере литобзора.

### 3.3 Структура проекта

```
ingest/        # выгрузка из обоих источников
db/            # ORM-модели, схема, загрузка
process/       # очистка, восполнение, производные параметры, флаги явлений
analysis/      # движок критериев и детектор критических периодов
viz/           # графики, тепловые карты, временные шкалы
data/raw/      # сырые выгрузки (кэш, в .gitignore)
data/clean/    # обработанные данные
config.yaml    # координаты станции, период, пороги риска
```

### 3.4 Схема БД (расширена относительно ТЗ п. 13.1)

Заданные в ТЗ таблицы не покрывают все параметры п. 8 — схема расширена. Это
согласованное отклонение (отметить в отчёте).

**weather_data**
- `id` INTEGER PK
- `datetime` TIMESTAMP
- `temperature` FLOAT
- `humidity` FLOAT
- `wind_speed` FLOAT
- `wind_gust` FLOAT          (добавлено)
- `precipitation` FLOAT
- `snowfall` FLOAT           (добавлено)
- `precipitation_type` TEXT  (добавлено)
- `pressure` FLOAT           (добавлено)
- `ww_code` INTEGER          (добавлено: код наблюдённого явления)
- `icing_flag` BOOLEAN
- `source` TEXT              (добавлено: station / era5 / filled)
- уникальный индекс по `(datetime, source)` — против дублей при повторной загрузке

**critical_periods**
- `id` INTEGER PK
- `start_datetime` TIMESTAMP
- `end_datetime` TIMESTAMP
- `risk_level` TEXT
- `description` TEXT
- `justification` TEXT

**risk_factors**
- `id` INTEGER PK
- `factor_name` TEXT
- `influence_description` TEXT
- `severity` INTEGER          (балл = частота × тяжесть)

### 3.5 Критерии риска (из ТЗ п. 10 — стартовые значения, уточняются литобзором)

| Условие | Уровень риска |
| --- | --- |
| Температура ниже −25 °C | высокий |
| Переход через 0 °C | высокий |
| Мокрый снег | высокий |
| Гололёд | критический |
| Ветер > 15 м/с | высокий |
| Влажность > 90 % при отрицательной температуре | критический |

## 4. План IT-части (этапы)

Зависимости: 0 → 1 → 2 → 3 строго последовательны. Этапы 4 и 5 после готовности 3
можно вести параллельно.

- **Этап 0. Окружение и каркас.** Репозиторий, venv, `requirements.txt`, структура
  каталогов, `config.yaml`.
- **Этап 1. Слой загрузки (ingest).** Выгрузка ERA5 через Open-Meteo (GET `/v1/archive`,
  запрос по годам, кэш сырого JSON на диск). Парсер станционных архивов rp5/meteo.ru
  (CSV/Excel). Каждый источник пишет в свой сырой файл с пометкой источника и версии.
- **Этап 2. Слой хранения (БД).** ORM-модели SQLAlchemy по схеме 3.4, генерация БД,
  загрузка через `to_sql`, индексы.
- **Этап 3. Слой обработки (process).** Очистка (дубли, физически невозможные выбросы,
  журнал пропусков); восполнение пропусков из ERA5 с пометкой `filled`; расчёт
  производных (переходы через 0 °C, длительность отрицательных температур, суточные
  перепады); флаги явлений из WW-кодов, где нет — прокси-критерий с отдельной пометкой.
- **Этап 4. Движок критериев и критических периодов (analysis).** Простановка уровня
  риска по порогам из конфига; группировка подряд идущих рисковых отсчётов в интервалы;
  запись в `critical_periods` с автозаполнением обоснования (условия, механизм, уровень,
  источник) по требованиям ТЗ п. 12.
- **Этап 5. Визуализация (viz).** Годовой/многолетний ход температуры, влажности,
  осадков; тепловая карта «месяц × фактор риска»; временные шкалы критических периодов;
  рейтинг факторов (заполнение `risk_factors`).

## 5. ПЕРВАЯ ЗАДАЧА — вертикальный срез (начни с этого)

Цель — убедиться, что мы дотягиваемся до обоих источников, и прогнать пайплайн
насквозь на минимальном объёме, прежде чем строить слои по отдельности.

1. Каркас проекта по структуре 3.3 + `config.yaml` с координатами Кандалакши и
   тестовым периодом (один год).
2. Выгрузить **один год** данных по Кандалакше из **обоих** источников:
   ERA5 (Open-Meteo) и станция (rp5/meteo.ru). Сохранить сырые файлы в `data/raw/`.
3. Создать SQLite-БД по схеме `weather_data` (3.4), загрузить оба массива с
   проставленным `source`.
4. Построить один контрольный график температуры за год по обоим источникам на одних
   осях — это сразу покажет, насколько ERA5 и станция согласуются.
5. Кратко доложить: за какой период станция реально отдаёт WW-коды явлений, сколько
   пропусков, как стыкуются источники по времени.

Этот срез вскроет проблемы стыковки слоёв раньше, чем мы вложимся в каждый слой
отдельно. После него — расширять по этапам 1→5.

## 6. Конвенции для агента

- Все пороги и параметры — через `config.yaml`, не хардкодить.
- Каждая запись данных хранит свой `source`; восполненные и прокси-значения помечаются
  явно.
- Сырые выгрузки кэшировать на диск; не перевыгружать без необходимости (воспроизводимость).
- Отчётные артефакты, которые понадобятся для пояснительной записки: SQL-скрипты схемы
  (из ORM), журнал обработки пропусков, методические пометки по прокси-критериям.
- Код модульный по слоям (ingest / db / process / analysis / viz), без перемешивания
  ответственности.
- Веди короткий журнал решений по спорным данным (как восполняли, как трактовали коды) —
  это спрашивают на защите.
